# 角色配置版本固定

QwenPaw 继续管理原生角色、会话和记忆。扩展只为工作流记录角色配置版本，并在已有插件检查点比较：同一 Agent ID 改了模型、工具权限或提示后，旧任务不能静默采用新配置。没有新增服务、记忆引擎或流程调度器，也没有上游源码补丁。

## 配置与冻结位置

双认证的插件 `GET /api/agent-line/execution-binding` 返回 `roleRevisions`，按受管协调角色 ID 映射到 `qwenpaw-role-v1:<64位小写SHA256>`。摘要同时包含该协调角色和固定 Codex 目标的配置，不返回提示或凭据正文。

可信部署将选定值保存在现有服务 `bindings.<bindingId>.roleRevision`。发布回执、原运行快照、任务顶层 payload、父投递账本和插件原任务绑定逐层保留该值。浏览器不能额外传入可信 roleRevision，模型任务输入中的同名值没有授权作用。新版本部署不能覆盖旧发布或运行里的摘要；重复旧操作仍返回原回执。

发布使用部署已配置的值，不自动把远端最新值认可为旧任务版本。Discovery 发现当前绑定与冻结值不符会阻止新任务登记；执行前还会向实际插件核对。因此发布成功本身不代表实际角色配置当前仍兼容。

摘要包含有效模型选择、所选模型的有效执行参数和能力、提供器连接配置、角色行为设置、相关全局权限默认值，以及按顺序读取的提示文件内容。使用官方模型解析、生成参数合并、协议及思考控制接口，不另写模型目录解析器。角色名、描述、无关角色登记、原生记忆目录与官方 AGENTS.md memory 标记区不进入摘要；正常记忆更新继续使用原生实现。固定 Codex 目标必须明确配置 model，未解析的 CLI 隐式模型会被拒绝，不能冒称已经固定。

当前摘要输入包含 `revisionSchema=2`，外部字符串仍使用 v1 格式，数据库结构不变。官方启动刷新目录的观测时间、价格、显示信息和无关模型增删不再使角色版本失效；所选模型的有效能力、生成参数、协议或思考控制变化仍会失效。所选模型被移除、标记远程缺失或要求重新确认付费时拒绝新执行；检查不主动请求模型或网络。原算法的历史摘要不自动追认为新算法结果，应在可信部署配置中显式采纳新角色版本并重新验收；可沿用原绑定 ID，已有发布、任务、回执和原生记忆保留。新任务冻结新值，旧发布与当前配置不一致时继续拒绝新运行，不改写历史来消除差异。

提示源仅接受限定 Markdown 文件名、普通文件，拒绝符号链接和 FIFO，单文件最多1MiB、合计4MiB，并核对读取前后身份。字段无法解析或配置不可读时拒绝新执行。

## 当前部署与只读角色限制（2026-10-22）

正式服务仍使用 `native-loop-parent` 与原开发角色、原测试策略，仅显式更新当前角色修订；未新增正式绑定。最终源码下的新任务已通过实际 Codex、独立三个 unittest 与资源退出核对，生成新的执行准入证明。目录刷新前后两次宿主启动的开发角色摘要一致，原七份 Agent 配置与九条旧任务完整行保持。

插件可选 `execution_bridge.readonly_role_ids` 使用官方单任务 `backend_controls` 为所列角色传递 `read-only / never`；不改变固定 Codex 目标的持久配置。可信控制会冻结到原执行回执与版本中；模型输出不能自行授予权限。此能力未发布主服务绑定：真实规划探针虽然记录了只读上下文，但 shell 因 Codex 缺少 `bwrap` 退出 101，不能证明实际读取或拒写。保留原任务与失败证据，不降级沙箱、不增加依赖，也不将独立基础产物测试通过当作只读权限验收通过。原生 Agent 与 ReMe 不受替换。

## 执行检查与用户提示

- Dispatcher 在取得执行 claim/工作区租约前核对固定版本。缺少、变化或暂不可查时保持 registered，分别保存 required/mismatch/unavailable 诊断；重复轮询不堆积相同事件。列表和详情显示中文原因，未启动任务不冒充执行资源已退出。
- 成功预检的内部证明只可用于同 gateway、同 task、同摘要，并消费一次；不是请求参数，也不接受 JSON 替代。它避免取得租约后再做一次失败的重复 GET。插件 bind 仍检查当前实际配置。
- 插件把原摘要持久绑定到原角色/会话。已有 middleware 在 reply、reasoning、model_call、检索/委派工具前核对；固定执行桥在新 claim 前再次核对。没有摘要的旧绑定不能自动补入当前摘要再新执行。
- 已提交任务的原身份观察、取消和退出核对不依赖当前角色摘要；已 claim 的相同载荷重放只观察。配置变化不能成为重投原父任务的理由。

原生修改 API 与插件检查后调用不是一个原子事务，不能据此宣称消除任意时序的热修改竞态。bind 已发送但回执未知时继续保留 intent，不重投；即使明确409，也不凭该响应推断所有外部执行资源不存在，仍需独立核对。本切片没有绕过未知执行的租约保护。

## 插件执行库升级

执行回执库需要 schema 4；沿用同一数据库，仅为 role_bindings 增加可空 role_revision。`ReceiptLedger.migrate(path)` 是显式迁移入口，正常打开和插件加载不会自动迁移。

正式切换前须排空对应写入方并取得一致备份。旧 schema 3 迁移后原绑定的摘要仍为 NULL，不追认最新配置；历史观察/取消保留，新的推理/委派拒绝。库缺失、版本错误或初始化失败时，插件保留受管角色 middleware，并明确503/degraded；不能让官方 loader 跳过整个失败插件而意外移除保护。

项目 QwenPaw 实例现已在排空可核对的执行后完成受影响组件备份、停机显式迁移与官方 CLI 插件安装，随后复用原端口启动。认证 health 和 execution-binding 返回可用，两个受管角色均可读取版本。原31条执行回执、27条角色绑定和7条撤销记录的旧列逐行保持，旧27条绑定的版本仍为 NULL；QwenPaw 配置语义未变，安装时7个插件文件与源文件逐字节一致。证据位于 `var/plugin-upgrades/role-revision-v1/report.json`。

备份范围是受影响插件、执行账本及相关配置，不是整个安装或 Sim 的完整回退。主适配服务的维护守卫与 unknown 准入保持，未启用 authoringFile/taskFlowFile；能力接口也不因插件健康而自动授予执行能力。此次部署没有修改官方源码、原生记忆实现或角色模型配置。主服务正式执行与完整升级验收仍需单独完成。

独立复核确认：两个此前 finished 的原生后台父任务在宿主重启后官方 GET 返回404；它们的临时查询状态并非持久历史。扩展主服务保存的两个旧任务仍可认证查询，均为原 succeeded/资源已释放。不能把持久账本可读等同于原生后台查询跨重启保留，尤其不能推断在途任务可自动续跑。详见上述目录 `root-secondary-check.json` 与 `report.json`。
