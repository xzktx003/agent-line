# 内置工作流模板目录扩充计划

## 目标

将前端内置模板从 2 个扩充到 20 个，覆盖需求交付、缺陷修复、排查、审查、升级、性能、文档、接口、迁移、发布准备、兼容修复、重构和架构决策等明确场景。每项目录元数据包含中文适用说明、输入契约、输出契约和完成定义。

## 边界与约束

- 保留 `delivery-review-v1`、`bounded-repair-v1` 标识及其现有图形语义。
- 新图只使用当前支持的 agent、condition、human、end、有限 loop 节点；不增加运行框架、依赖、后台调度或节点类型。
- 模板只生成草稿。不得包含本地/项目路径、凭据、真实角色标识、历史结果或发布身份。
- 每个槽位由现有当前项目角色绑定映射；不同槽位必须映射到不同正式角色，同一槽位可在多个阶段复用。所有 Agent 均使用 `native-role` 记忆策略。
- 任何代码写入只交给固定开发角色；规划与审查角色明确只读。所有条件以本轮真实 `result.verificationStatus == passed` 为准；人工决定只认布尔 `approved == true`，并提供拒绝出口。
- Agent 提示说明权限边界，但不能代替后端权限控制；如果后端无法保证只读角色或固定角色委派，必须拒绝执行。

## 实施方案

1. 扩展模板展示元数据，不暴露内部配方或可变共享对象。
2. 用小型配方描述复用 Agent、独立验收、人工审批与有界修复的固定图形；保留两个旧模板的专用分支以维持原图语义。
3. 为 18 个新增业务场景定义不同流程顺序与角色槽位，审批前置门和终态人工门显式建图。
4. 保留角色映射严格校验、节点 ID 前缀 ASCII/长度校验、真实验收状态条件和布尔人工审批条件。

## 静态验收标准

- 目录正好 20 项且 ID 唯一，两个原 ID 不变。
- 每项均有中文 `inputContract`、`outputContract`、`completionCriteria`。
- 新场景在流程阶段、审批位置、角色组合或结束产物上体现具体业务差异，不是单纯改名。
- 新图只引用支持节点；写代码阶段固定映射到开发槽位，规划/审查阶段指令只读。
- 所有拒绝、验收失败均可到明确结束节点；新模板以草稿图作为输出，不含发布动作。

按用户要求，本任务只进行源码静态阅读与静态复核，不运行测试、Node、浏览器、lint、探针或生产模块导入；因此不声称编译或执行通过。
