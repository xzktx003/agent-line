# 业务尝试次数与单次执行时限

既有任务接口的 `limits` 已接入原任务库和执行巡检，不新增预算数据库、调度器、依赖或上游补丁。限制覆盖一次受控任务的父角色准备、委派和实际执行等待；业务尝试次数不是模型调用次数。

## 使用和冻结

`POST /extension/v1/node-tasks` 沿用 `limits.maxExecutionSeconds`（严格整数 1–86400）和 `limits.maxBusinessAttempts`（严格整数 1–100）。未传字段的新 HTTP 请求沿用此前已经声明的默认值：3600 秒、3 次；本次使这些限制实际生效。既有数据库中完全没有 limits 的历史记录保持原行为，查询不虚构默认限额，不改写历史。

同一 projectId、workflow.id、workflow.runId、workflow.nodeId 组成业务尝试额度组。首登记冻结两个限制，后续尝试不能通过换角色、发布版本、激活 ID 或省略 limits 扩大额度；更改限制应使用新的流程运行。同组既有无限额旧记录时拒绝混入新的限额记录，不推断旧历史已经具备可信额度。组版本、事件记录缺失或损坏时失败关闭。

原 claim 的 BEGIN IMMEDIATE 同时检查 FIFO、工作区租约及历史提交意图，并原子记录 submission_intent。只有成功提交意图才消耗一次；失败、超时、取消和回执未知均不退款。登记后尚未提交便取消不耗额度。额度耗尽的任务保持已登记并显示原因，不调用执行网关；明确耗尽且未提交、无租约的记录不会永久挡住另一节点的可运行队列。普通暂停、配置待核对和未知执行仍保留原阻塞语义。

## 到期与停止

每次执行以唯一 submission_intent 的持久时间加 maxExecutionSeconds 计算截止时间，排队时间不计入。重复、非法或未来时间戳以及活动任务丢失意图均不能当作“尚未超时”。观察服务会先核对原执行；原执行尚未终止且已到期时，发出既有停止请求。继续流程检查也会拒绝已到期的活动任务。

这是巡检触发的取消请求，实际取消受网络、后端能力和巡检延迟影响，不保证到秒终止进程。取消回执未知时仍为停止待确认，保留身份和工作区租约；只有原生终态及可信退出回执才可释放。已经核对到终态的结果保留，不因稍晚到达的巡检删除产物或重新编码。适配服务重启从同一数据库读取原意图和额度，不自动重投。

## 页面与用量

授权任务详情和列表接口增加 executionLimits 投影，包含当前节点组、已提交业务尝试数、冻结上限、本次时限和 Unix 秒截止时间；这是本地业务额度信息，不代表完整执行准入。真实 token、父角色/Codex 模型调用数和费用缺少可信来源，usage.tokens、modelCalls、cost 明确为 null。异常组显示待核对，不能当成已用零次。

任务详情沿用原中文列表展示限额和未知用量，额度耗尽有中文队列原因；没有费用估算。项目认证和路径隐藏保持，退出清空页面，旧后端未提供该字段时不展示。2026-10-23另在编辑器源码接通可选节点限额表单与发布/运行冻结，后端已按原配置重载，尚未做功能验收，见[节点限额配置](node-limits-editor.md)。
